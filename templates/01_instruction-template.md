# 検証基準付き指示テンプレート

> 対象: 全体（開発フェーズで全員が使用）／ 所要時間: 記入 5〜10 分／ 前提: なし（読むと理解が深まる →
> [検証できる指示の基本形](../10_beginner/03_instruction-basics.md)）

## この資料で分かること

- AI へ実装・調査を依頼するときの、検証基準付き指示の標準フォーマット
- 自動テストで検証しにくいタスク（UI の見た目・データ分析等）向けの完了条件の書き方
- 記入済みの具体例 3 パターン（実装／調査／自動検証が難しいタスク）

## なぜ必要か

「検証できる指示」は本学習会でもっとも重要なスキルです。考え方の解説は
[検証できる指示の基本形](../10_beginner/03_instruction-basics.md)（初心者向け）と
[検証可能性と指示設計](../20_intermediate/02_verifiability.md)（中級・発展編）にまとめています。

本テンプレートはその考え方をそのままコピーして使える形式にしたものです。開発フェーズでは、
このテンプレートを起点に AI への指示を書くことをお勧めします。完了条件（検証基準）が
書けないタスクは、まだ分解が足りていないサインです。

## テンプレート

```text
【目的】
（何のための変更か。背景・解決したい問題を 1〜3 行で）

【参照情報】
（読むべきファイル・仕様書・既存実装。パスを明示）
-

【作業範囲】
（変更してよいファイル／変更してはいけないもの）
- 変更可:
- 変更不可:

【制約】
（守るべき規約・技術的制約）
-

【完了条件】※検証基準を必ず含める
1. （実行可能なテストコマンドと期待結果、または CLI・画面での確認手順と期待結果）
2. （自動検証が難しい場合はスクリーンショット比較や手動チェックリストで代替する）

【報告に含めるもの】
- 変更ファイル一覧と要約
- 実行した検証コマンドと結果
- 事実／推測／未検証の区別（未検証事項は明示すること）
```

「報告に含めるもの」の書き方に迷ったら、このリポジトリ自身が使っている
[PR テンプレート](../../.github/pull_request_template.md)（実装 PR に何を書くかの実例）も参考になります。

## 記入例 1: 実装タスク

```text
【目的】
FAQ 検索画面で、キーワードの部分一致検索をできるようにする。
現状は全件表示のみで、目的の FAQ にたどり着けない。

【参照情報】
- 検索画面: src/app/faq/page.tsx
- FAQ 取得 API: src/app/api/faq/route.ts
- 入力検証の既存例: src/app/api/items/route.ts（この検証方法を踏襲）

【作業範囲】
- 変更可: 上記 2 ファイルと対応するテストファイル
- 変更不可: DB スキーマ、共通コンポーネント

【制約】
- 検索クエリはサーバ側で入力検証すること
- 既存のカテゴリ絞り込みと併用できること

【完了条件】
1. npx vitest run src/app/api/faq/route.test.ts が pass
   （検索あり／なし／該当 0 件／不正入力の 4 ケースを含む）
2. 開発サーバで /faq?q=パスワード を表示し、部分一致した FAQ のみ表示されること

【報告に含めるもの】
- 変更ファイル一覧と要約
- テスト実行結果（コマンドと出力）
- 未検証事項があれば明示
```

> 上記の `npx vitest run ...` は Next.js / Vitest を使う場合の一例です。自分の技術スタックの
> テストコマンド（`pytest` / `go test` / `npm test` 等）に読み替えてください。

## 記入例 2: 調査タスク

```text
【目的】
既存の通知処理の仕組みを把握したい。新しい通知種別を追加する前の事前調査。

【参照情報】
- src/lib/notification/ 配下一式
- 通知に関する仕様メモ: docs/notification.md

【作業範囲】
- 読み取りのみ。ファイルの変更は一切しないこと

【制約】
- 事実として挙げる項目には、必ず根拠（ファイルパスと該当行）を付けること
- 推測で補った箇所は「推測」と明示すること

【完了条件】
1. 通知の送信経路（トリガー → 処理 → 配信）を図または箇条書きで説明
2. 新種別追加時に変更が必要なファイルの一覧（それぞれ根拠となる行を引用）
3. 不明点・未検証事項のリスト

【報告に含めるもの】
- 上記 1〜3
- 参照したファイルの一覧
```

## 記入例 3: 自動検証が難しいタスク

UI の見た目の調整やデータ分析のように、テストコードだけでは判定しにくいタスクもあります。
その場合は完了条件を「スクリーンショット比較」や「手動チェックリスト」として書きます。

```text
【目的】
トップページのヒーローセクションを、スマートフォン幅でも崩れないレイアウトに直す。
現状は横幅 375px 未満で画像とテキストが重なって表示される。

【参照情報】
- 対象コンポーネント: src/components/Hero.tsx
- 現状のスタイル定義: src/components/Hero.module.css

【作業範囲】
- 変更可: 上記 2 ファイル
- 変更不可: 他のセクションのレイアウト

【制約】
- 375px・768px・1280px の 3 幅で崩れないこと

【完了条件】
1. 375px・768px・1280px の 3 幅でスクリーンショットを撮り、変更前後を並べて比較し、
   画像とテキストの重なりが解消されていること
2. 手動チェックリスト: (a) 画像が見切れていない (b) 見出しが折り返されている
   (c) ボタンがタップ可能な大きさで表示されている — の 3 点をすべて満たすこと

【報告に含めるもの】
- 変更ファイル一覧と要約
- 変更前後のスクリーンショット（3 幅分）
- 手動チェックリストの結果
```

## やってみよう

直近で AI に依頼したい作業を 1 つ選び、このテンプレートで指示を書いてみましょう。
完了条件（検証基準）が思いつかない場合は、タスクをもう一段細かく分解してみてください。
