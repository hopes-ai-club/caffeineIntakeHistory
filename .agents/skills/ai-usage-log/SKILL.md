# AI Usage Log

通常作業と通常作業分のコミットが完了した後、その作業をAI活用ログへ記録するか確認する。このファイルをClaude CodeとCodexに共通する記録ルールの正本とする。

## 仕組みと責務

- `git-workflow` Skillが、通常作業の変更・検証・コミット・push完了後にこのSkillへ引き継ぐ。
- このSkillが、記録要否の確認、作業ユーザーと既存形式の判定、ログ内容、別コミットの手順を管理する。
- `CLAUDE.md`とツールごとのSkill入口は正本への導線だけを持ち、記録ルールを複製しない。
- ツール固有のフックは使わない。明示的なユーザー確認を必要とする対話手順を、Claude CodeとCodexで同じSkillとして実行する。

## 記録対象と確認タイミング

コード、文書、設定、デザイン、検証記録など、リポジトリの成果物を変更して通常作業分のコミットを作成した作業を対象にする。次は対象外とする。

- リポジトリを変更しない相談・説明・調査だけの作業
- 未完了またはコミット前で止まった作業
- AI活用ログそのものの作成・更新

通常作業分のコミットが成功し、pushを行う作業ではそのpushも完了した後、Pull Request作成前に「今回の作業についてAI活用ログを作成・追記しますか？」と明示的に確認する。先にログを変更しない。ユーザーが現在の会話ですでに記録を明示的に依頼している場合は、その依頼を承認として扱い、同じ質問を繰り返さない。

- 承認された場合だけ、以下の手順でログを変更する。
- 作成しないと回答された場合は、ログを変更せず通常のPull Request確認または完了報告へ進む。
- 回答が曖昧な場合は、ログを変更せず確認する。

## 作業ユーザーと既存運用の特定

1. `git config user.name`と`git config user.email`を確認する。GitHubを利用する作業では`gh auth status`も照合し、作業ユーザーを特定する。
2. `members/<作業ユーザー>/logs/`だけを調べる。Git設定、GitHubログイン、メンバーディレクトリの対応が一意でなければユーザーへ確認する。
3. 対象ユーザーの既存ログがあれば、ファイル名と見出しの対象期間から判断した最新のログを中心に次を確認する。ファイルの更新日時だけで決めない。
   - 月別、週別、単一ファイルなどの分割単位
   - 保存先とファイル名
   - 見出しの境界と並び順
   - 項目構成、表記、リンク形式
4. 作業日が分割単位の境界をまたぐ場合は、既存運用に従って対象ファイルと見出しを選ぶ。月別運用の場合だけ、作業日の月のファイルを選び、必要なら既存形式を踏襲して月・週見出しを追加する。
5. 既存ログがない、複数の形式が競合する、または対象ファイルを一意に決められない場合は、`templates/02_ai-usage-log.md`を基準に保存先・ファイル名・構成の候補を提示し、ユーザーの確認を得るまで作成しない。

他メンバーのログは変更しない。

## 記録内容

実際の作業差分、検証結果、通常作業分のコミット、Issue、既存Pull Requestと整合する内容だけを書く。少なくとも次を含める。

- 日付
- 工程
- 実際に使用したAIツール
- タスク概要
- 採用状況

既存形式に欄がある場合、または有用な情報がある場合は、プロンプトの要点、手戻り・誤り、所要時間、学び、実施した検証、未検証事項、コミット・Issue・Pull Requestへの参照も記録する。

- プロンプト全文、個人情報、認証情報、秘密情報、実データは記録しない。プロンプトは再利用可能な要点だけにする。
- 実測していない時間や未確認の結果を推測しない。既存形式に値が必要なら「未計測」「未検証」「未作成」などを明記する。
- Pull Requestがまだ存在しない場合、参照は省略するか既存形式に合わせて「未作成」とする。

## 再開・追加修正

対象ユーザーの既存ログ全体から、同じIssue、Pull Request、ブランチ、通常作業コミット、または明らかに同一のタスク概要に対応するエントリを検索する。同じ作業の再開や追加修正なら新しいエントリを増やさず、既存エントリへ差分、検証、コミット参照を追記・更新する。独立した目的と成果物を持つ別作業だけを新規エントリにする。判断できない場合はユーザーへ確認する。

## 変更とGit操作

対象ユーザーのログだけを編集し、Markdownの見出し・表・リンクと`git diff --check`を確認する。既存の未コミット変更を上書き、破棄、stageしない。

ログ変更は通常作業分のコミットへ混ぜない。プロジェクトの`git-workflow` Skillに従い、ログ差分について改めてコミット前確認を提示し、明示的な承認後に対象ログだけを別コミットとしてstage、commit、pushする。ログコミット自身について、このSkillを再度起動しない。ログ処理が終わった後に通常のPull Request確認へ進む。

ログの作成・追記やpushに失敗した場合は、黙って通常作業を完了扱いにせず、失敗理由、未反映の対象ファイル、安全な手動対応方法を伝える。
